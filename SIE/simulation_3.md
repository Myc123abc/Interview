## std::unique_ptr と std::shared_ptr の違いについて説明してください。また、ゲームエンジンを開発する場合、どのような場面でそれぞれを使い分けますか？
```
はい。
unique_ptrとshared_ptr(シェアード　ポインタ)、またweak_ptrもありますね。
どれもオブジェクトをメモリで保存し、ポインタにより、訪問しますね。
でもweak_ptrはちょっと特殊で、実装の開発中でもありまり使用されないです。

unique_ptrとshared_ptrの区別は、unique_ptrは、ただ一つの対象が、このメモリが、所有します。
ポインターに対して、コーピーができない、ムーブだけができます。
C++のなかでよくnewとか、手動でメモリを割り当てるのことを代わって、使用されています。

はい、ではshared_ptrは、メモリのオブジェクトに、参照カウントを追加します。

でも、ただ訪問のことが安全です、メモリ自体の読む書くは安全ではないので、
こちらは注意が必要です。
ゲームエンジンの開発には、shared_ptrに利用されるところは、スレッドプールを設計中に、タスクの対象として、
```

## C++のコピーコンストラクタとムーブコンストラクタの違いについて説明してください。
```
ムーブコンストラクタはよく使っています。
ムーブの場合は、ほぼ内部のポインタをコーピーすることだけです。
コーピーならば、メモリの全部の内容がコーピーする必要なことです。コストにほよくおおいです。
一般的には、ムーブが使えれば、ムーブを使います。
時々コーピーの語彙が必要な場合は、コーピーを利用します。
ムーブに関しては、よく利用される場合は、ファンクションにローカルオブジェクトを新規し、
そして、このオブジェクトを戻り値としてすることです。
ここは、特に手動でムーブを指定し、コンパイラが自動的にムーブをします。
ゲームエンジンの中にも、多くの対象を、コーピーしなく、ムーブを構造することで、よりいい性能が取得できると考えます。
以上です。
```
## std::vector に要素を追加していったとき、vectorの容量（capacity）が足りなくなった場合、内部では何が起こるでしょうか？また、ゲームエンジンのように大量のデータを扱う場合、この再確保（reallocation）が性能にどのような影響を与える可能性がありますか？
```
はい、ベクターは、新規対象を追加のとき、容量（ようりょう）が足りない場合は、内部のメモリを、新たに割り当てるメモリをコーピーし、
元のメモリを割り当て済みをしますね。
ゲームエンジンでは、ベクターを使用する場合は、もし容量足りないで、メモリをコーピーした場合は、ゲームに対して突然フリーズした、一瞬です。
ここは簡単な操作は、事前に足りるのスペースを割り当てて、大部の場合は大丈夫です。
他のもっと良いの方法があるかもしれないですね。
以上です。
```
## std::vector の要素を追加・削除した場合、既存の要素へのポインタ、参照、イテレータは常に有効でしょうか？
```
はい。これも注意必要な点ですね。
先みたいに、ベクターにへ追加する場合は、内部のメモリを再割り当てることがあります。
この場合は、既存のポインタ、参照、イテレータとかは、無効になります。
でも、削除の場合は、無効かどうかとは確定できない。
ただオブジェクトを削除すれば、メモリの容量も保存し、ポインタとかも有効な感じてすね。
でもベクターがデストラクタの場合は、きっと無効になる。
たとえ、ポインタによる、以上なメモリはまだ書いたなかったでも、続いて使用することは危険です。
これは注意必要です。
以上です。
```
## C++の virtual 関数について説明してください。
```
はい。バーチャルは派生（はせい）したクラスの関数を使用した場合は、派生する関数を使用するか、それとも基底（きてい）の関数を使用するかと決定します。
もし派生のクラスには、基底のバーチャル関数を定義すれば、派生の関数を利用します。定義されないの場合は、基底の関数を利用します。
また、基底クラスのデストラクタをバーチャルが必要な場合は、派生の対象に対して、対象をデストラクタをする場合、ただ自分のデストラクタをする、基底のは呼び出しないの場合、
バーチャルを使用します。でなければ、派生のデストラクタを使用済み後、基底のデストラクタも使用します。という形になります。
以上です。
```
## C++の std::mutex と std::atomic の違いについて説明してください。
```
はい。ミューテックスとアトミックはどっちも同期で使用されることですよね。
ミューテックスは特定な場合でロークして、ロークを解放して、スレッドセーフを保障します。
アトミックは使用者が変数の使用方によって、異なるメモリ順序が指定できます。
よりいい性能が取得できます。
でも、アトミックは全部のスレッドセーフの使用ケースができなくではないので、ミューテックスの使用必要な場合もあります。
以上です。
```
## ゲームエンジンで、複数のスレッドが同じ std::vector に対して、同時に push_back() を行う必要があるとします。

```
これで安全にマルチスレッド中利用ができます。
また、性能特に注意されますの場合も、ロークフリーの設計も考えることができます。
でも全部の場合は利用できるではないのです。一番使用が良いの場合は使用するのがいいと思います。
```

## あなたがゲームエンジンを設計するとき、メモリ管理についてどのようなことを意識していますか？
```
はい、メモリの頻繁（ひんぱん）的に確保と解放は、時間が長くなると、小さなメモリボロックが残ります。
これは長期的に運行されるプログラミングには、メモリ不足の問題が発生する可能です。
それを解決するため、プログラミング自体に、メモリプールを使用することは一般的です。
メモリプールを使用して、自分でメモリを管理する、解放されたメモリも一つ大きいなメモリを整合して、メモリを高い利用率もできます。
以上です。
```

```
頻繁な確保・解放によって、アロケーションのオーバーヘッドが増えたり、メモリが断片（だんぺん）化したりする可能性があります。そのため、ゲームエンジンでは用途（ようと）によって、メモリプールなどを利用することがあります。
```
